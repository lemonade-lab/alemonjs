# AlemonJS 研究复盘设计

本设计将 [研究方向](./research-directions.md) 转换为持续复盘机制。复盘的目的不是汇报完成了多少任务，而是回答：假设是否被证据支持、投入是否值得继续、下一轮应保留、调整或停止什么。

## 1. 复盘边界与节奏

| 类型         | 触发时机                                   | 范围             | 必须产出                       |
| ------------ | ------------------------------------------ | ---------------- | ------------------------------ |
| 方向复盘     | 每个迭代结束                               | 活跃研究方向     | 指标变化、结论、下一步决策     |
| 实验复盘     | PoC、压测、故障注入完成后                  | 单个实验         | 基线、方法、结果、可复现步骤   |
| 事件复盘     | 线上故障、数据丢失、凭据泄露风险或发布回滚 | 相关链路         | 时间线、根因、修复与预防项     |
| 季度组合复盘 | 每 2–3 个迭代                              | 全部方向及优先级 | 方向升降级、资源调整、废弃决策 |

任何 P0 事故都不等待迭代结束：先完成事件复盘，再将预防工作纳入方向复盘。

## 2. 统一复盘流程

```text
研究假设 → 最小实验 → 数据/日志/测试证据 → 复盘评审
                                              ├─ 继续：扩大验证或产品化
                                              ├─ 调整：修正假设、范围或指标
                                              └─ 停止：记录反例和替代方案
```

每项结论必须关联可访问的证据，例如测试结果、压测报告、脱敏日志样本、协议契约输出或已合并的变更；“感觉更稳定”不作为结论依据。

## 3. 方向复盘卡

每条活跃方向每个迭代填写一张卡。状态仅可为“探索中 / 验证中 / 产品化 / 暂停 / 停止”。

```md
## <方向名称> — <迭代或日期>

- 状态：探索中 | 验证中 | 产品化 | 暂停 | 停止
- 负责人：
- 原始假设：
- 本轮要回答的问题：
- 基线：<日期、版本、运行环境、数据来源>
- 本轮改动或实验：
- 指标结果：<目标、实际值、与基线差异>
- 证据链接：<测试、报告、日志样本、ADR、PR>
- 意外结果/风险：
- 决策：继续 | 调整 | 停止
- 下一步：<单一、可验证的动作；负责人；截止迭代>
```

## 4. 方向指标面板

| 方向           | 核心结果指标                             | 过程指标                                    | 退出或升级条件                                             |
| -------------- | ---------------------------------------- | ------------------------------------------- | ---------------------------------------------------------- |
| 运行时可靠性   | 优雅退出成功率、重连恢复时间、残留句柄数 | 生命周期测试覆盖的场景数                    | 覆盖信号、IPC stop、启动失败、断连；无阻塞性缺口后转产品化 |
| 可观测性       | 故障定位时间、敏感字段泄露数             | 含 traceId 的关键事件比例、结构化日志覆盖率 | 核心请求链路可关联，脱敏扫描无高危项                       |
| 平台适配与 CBP | 契约通过率、兼容模式事件丢失率           | 已覆盖的能力和协议版本数                    | 当前及受支持旧协议的关键契约全部通过                       |
| 安全与配置     | 启动前拦截的错误比例、脱敏覆盖率         | schema 覆盖的配置项比例                     | 高风险配置均在启动前验证，敏感字段无明文输出               |
| 测试与发布质量 | 回滚次数、回归发现时间                   | CI 通过率、核心回归集覆盖率                 | 发布门禁自动化，可复现最近一次发布验证                     |
| 开发者体验     | 首次可运行时间、自助解决率               | doctor 检查项和有效诊断比例                 | 新项目可按文档完成运行并定位常见配置问题                   |
| 性能与容量     | P95/P99、资源消耗、消息丢失率            | 已覆盖的并发档位数、基线更新频率            | 已给出支持容量和超过容量时的退化行为                       |

指标初期不预设虚假目标值。第一轮只建立可复现基线；第二轮以后才根据基线设定目标和告警阈值。

## 5. 事件复盘模板

```md
# <事件标题>

- 级别：P0 | P1 | P2
- 影响：用户、平台、消息、数据、时间窗口
- 发现方式：监控 | 用户反馈 | 发布检查 | 开发调试

## 时间线

| 时间 | 事实 | 证据 |
| ---- | ---- | ---- |

## 根因分析

- 触发条件：
- 技术根因：
- 为什么现有测试、监控或流程没有阻止：

## 行动项

| 行动 | 所属方向 | 验收条件 | 负责人 | 截止迭代 |
| ---- | -------- | -------- | ------ | -------- |
```

事件复盘只描述可验证事实，不归因于个人。每个行动项必须有验收条件；“加强测试”应改写为具体测试场景和通过条件。

## 7. 决策规则

- **继续：** 指标改善或假设仍未被充分证伪，且下一步实验能显著降低不确定性。
- **调整：** 结果混合、成本过高或指标定义不充分；须明确修改的是假设、范围还是测量方式。
- **停止：** 假设被证伪、收益低于替代方案，或当前优先级不再成立；保留证据与重新开启条件。
- **升级：** P1/P2 方向出现 P0 风险，或已满足产品化门槛，需要调整优先级和发布计划。

## 8. 复盘输出的落点

- 指标与实验报告放入 `docs/research/`，按方向和日期存档。
- 架构取舍形成 ADR，并链接对应研究复盘卡。
- 可交付改动进入 issue/迭代计划；每项引用验收指标。
- 已停止研究的结论保留在文档中，避免再次投入到已证伪路径。

第一次方向复盘应先聚焦 P0 的“运行时可靠性”和“可观测性”，并把当前 logger 改造作为基线，而不是作为完成结论。
