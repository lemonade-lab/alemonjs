# AlemonJS 研究方向

本文把项目演进拆分为可独立推进、可验证、可组合的研究方向。每个方向先完成最小验证（PoC 或基准），再决定是否进入正式版本；不应仅以功能数量作为完成标准。

## 优先级概览

| 优先级 | 方向           | 预期收益                                 | 首个交付物              |
| ------ | -------------- | ---------------------------------------- | ----------------------- |
| P0     | 运行时可靠性   | 减少退出、重连和子进程异常造成的服务中断 | 生命周期与故障注入测试  |
| P0     | 可观测性       | 缩短定位消息、平台和网络问题的时间       | 结构化日志规范与关联 ID |
| P1     | 平台适配与 CBP | 提高平台接入的一致性和兼容性             | CBP 契约测试套件        |
| P1     | 安全与配置     | 避免凭据泄露、错误配置和不安全默认值     | 配置 schema 与脱敏策略  |
| P1     | 测试与发布质量 | 降低回归及跨版本兼容风险                 | CI 矩阵与发布检查清单   |
| P2     | 开发者体验     | 降低创建、调试和维护机器人应用的成本     | 脚手架和诊断命令        |
| P2     | 性能与容量     | 明确高消息量下的资源上限和退化策略       | 压测基线与容量报告      |

## 1. 运行时可靠性

**目标：** 平台进程、客户端进程和主进程在启动、停止、崩溃、重连时保持可预测的状态。

研究问题：

- 信号、IPC `stop`、启动失败、未捕获异常是否遵循同一套生命周期？
- 日志、文件传输、WebSocket 和定时任务在关闭前是否能完成或超时退出？
- 子进程重启的退避、上限和健康检查是否可配置且可观察？

验证指标：优雅退出成功率、重连恢复时间、重复启动幂等性、故障注入后的残留句柄数。

首个实验：为 `client`、`platform-bootstrap`、runtime store 建立同一份进程生命周期测试矩阵，覆盖 SIGTERM、IPC stop、启动失败及网络断连。

## 2. 可观测性与日志

**目标：** 在不暴露敏感信息的前提下，能从一次事件追踪到路由、平台调用、CBP 通信和最终结果。

研究问题：

- 是否应采用统一事件结构：`timestamp`、`level`、`message`、`data`、`error`、`traceId`？
- 一次消息或请求的关联 ID 如何跨 middleware、子进程 IPC 与 WebSocket 传递？
- 文本日志与 JSON 日志是否应由 `LOG_FORMAT` 切换？
- 哪些字段必须脱敏：token、authorization、cookie、password、消息隐私内容？

验证指标：一次故障从日志定位到根因的平均时间、敏感字段扫描命中数、日志体积及写入延迟。

首个实验：定义日志事件 schema，并在 HTTP 请求、事件处理和 CBP 连接链路植入同一个 `traceId`。

## 3. 平台适配与 CBP 协议

**目标：** 让新平台接入具备稳定的能力声明、错误语义与版本兼容边界。

研究问题：

- 平台能力（消息、媒体、群组、撤回、互动）能否显式声明并在运行时检查？
- CBP v1、当前协议与文件传输之间哪些字段必须向后兼容？
- 适配器失败时，何时回退、何时重试、何时向调用者返回明确的不可用错误？

验证指标：协议契约通过率、新平台最小接入代码量、兼容模式下的事件丢失率。

首个实验：把现有 CBP 文档中的示例整理为可执行的请求/响应契约测试，并在 CI 中运行。

## 4. 安全与配置治理

**目标：** 配置既易于使用，又不会因错误提交、日志输出或运行时读取而泄露凭据。

研究问题：

- `alemon.config.yaml`、环境变量和平台包配置的优先级是否明确？
- 是否应在启动前执行 schema 校验，并输出可操作的错误而非运行期异常？
- 日志、异常、诊断命令和 CBP 文件传输如何统一执行字段脱敏？

验证指标：启动前发现的配置错误比例、敏感字段脱敏覆盖率、配置迁移成功率。

首个实验：为配置定义 schema 与脱敏字段表；先覆盖 token、secret、password、authorization、cookie。

## 5. 测试、兼容性与发布质量

**目标：** 将核心行为从人工验证转为可重复的质量门禁。

研究问题：

- 哪些行为必须具备单元、集成和子进程端到端测试？
- 支持的 Node.js 版本、平台包版本及协议版本如何组成兼容矩阵？
- 发布前如何自动检查构建产物、exports、类型声明及变更日志？

验证指标：核心模块测试覆盖率、发布后回滚次数、兼容性回归发现时间。

首个实验：从 logger、配置加载、CBP 连接、进程生命周期四项建立最小回归集，并接入 CI。

## 6. 开发者体验与诊断

**目标：** 让开发者能够快速创建项目、发现配置错误并导出必要诊断信息。

研究问题：

- CLI 是否应提供 `doctor`、`logs`、`config validate`、`platform status`？
- 如何为平台包生成一致的模板、类型和本地调试入口？
- 是否应支持一键导出已脱敏的诊断包？

验证指标：首次可运行时间、常见问题自助解决率、诊断命令的有效信息比例。

首个实验：扩展现有 `alemonjs info` 为只读 `doctor`，检查 Node 版本、配置、平台依赖、端口和日志目录。

## 7. 性能与容量

**目标：** 明确事件吞吐、内存、文件句柄和日志 IO 的容量边界，并拥有可控退化策略。

研究问题：

- 高并发事件下 middleware、路由、IPC 和日志的瓶颈分别在哪里？
- 重复事件缓存、订阅映射和生命周期数据是否有明确上限与回收机制？
- 日志按日切割是否还需要单文件大小上限、异步队列水位线或采样？

验证指标：P95/P99 处理延迟、每千事件 CPU/内存、峰值文件句柄、消息丢失率。

首个实验：建立模拟事件压测器，输出 1、10、100 个并发会话下的基线报告。

## 推进方式

每个方向采用相同节奏：提出假设 → 最小实验 → 记录基线与结论 → 形成 ADR → 拆分可发布改动。P0 方向优先进入最近两个迭代；P1 在 P0 的接口稳定后并行；P2 以真实用户反馈和容量数据决定投入。
